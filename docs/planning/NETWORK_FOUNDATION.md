# 환율 API와 로컬 캐시

문서 버전: 2.0
기준일: 2026-11-10
상태: Frankfurter v2 홈 환율 조회·Room 캐시·통화 선택 구현 완료

## 목적

공통 HTTP 통신 기반과 Frankfurter v2 환율 계약을 사용해 3단계의 첫 기능인 홈 환율 조회를 제공한다. 환율 조회 성공 여부와 관계없이 기존 오프라인 여행 기능은 동작해야 한다.

## 네트워크 구성

- Retrofit 기반 타입 안전 HTTP 서비스
- OkHttp 연결·읽기·쓰기·전체 호출 타임아웃
- Kotlinx Serialization JSON 변환과 알 수 없는 필드 무시
- HTTP 오류, 연결 실패, 타임아웃, 잘못된 응답과 알 수 없는 오류 구분
- Hilt를 통한 네트워크 객체와 환율 서비스 제공
- Android `INTERNET` 권한

## Frankfurter v2 계약

- Base URL: `https://api.frankfurter.dev/`
- Endpoint: `v2/rates`
- Query: `base=KRW`, `date=yyyy-MM-dd`
- 응답: `date`, `base`, `quote`, `rate`
- 인증키가 필요하지 않는다.
- 기본 혼합 환율은 여행 예산 참고용 중간 기준 환율로 사용한다.
- 송금 받을 때·보낼 때 환율이나 실제 환전 수수료는 제공하지 않는다.
- `base=KRW` 응답은 1원당 외화 수량이므로 Repository Mapper에서 역수로 변환해 `외화 1단위당 원화`로 저장한다.
- 통화 코드는 `USD`, `JPY`, `VND` 같은 ISO 4217 코드를 사용한다.

## 저장 및 표시 규칙

- Room에는 통화 코드, 한국어 통화명, 외화 1단위당 원화 환율, 기준일과 조회 시각을 저장한다.
- 금액 계산용 원본 환율과 화면 표시 단위를 분리한다.
- `JPY`는 100단위, 1단위당 원화가 0.1원 미만인 통화는 1,000단위, 10원 미만인 통화는 100단위로 표시한다.
- 따라서 베트남 동은 `1,000 VND = n원` 형태로 표시하지만 계산과 저장은 1 VND 기준을 사용한다.
- 홈 환율 금액은 반올림해 소수점 첫째 자리까지 표시하고 저장된 계산용 환율 정밀도는 유지한다.
- 기존 한국수출입은행 캐시는 제공자와 단위가 다르므로 Room 5→6 마이그레이션에서 환율 캐시만 비우고 여행 데이터는 보존한다.
- 기존 `JPY(100)`·`IDR(100)` 선택값은 각각 `JPY`·`IDR`로 정규화한다.

## 갱신 규칙

- 앱 시작 화면은 마지막 정상 Room 캐시를 즉시 표시하고 최신 환율을 백그라운드에서 요청한다.
- 응답이 비어 있으면 최대 7일 전까지 이전 날짜를 조회한다.
- 성공 응답만 캐시에 반영하며 실패 시 이전 캐시를 유지한다.
- 예정·진행 여행의 예산 환산값은 최신 정상 캐시를 사용한다.
- 예산·지출 저장 시 원금액, 통화, 적용 환율, 환율 기준일과 환산 금액을 스냅샷으로 저장한다.
- 여행 종료일이 지난 여행은 저장된 스냅샷을 표시하고 최신 환율로 재계산하지 않는다.

## 보안과 운영 원칙

- Frankfurter 공개 API는 인증키를 사용하지 않으므로 앱과 로컬 설정에 환율 API 비밀값을 두지 않는다.
- 요청·응답 본문을 기본 로그로 출력하지 않는다.
- 일·월 쿼터는 없지만 남용 방지 제한을 고려해 앱 시작 시 한 번 갱신하고 Room 캐시를 우선 사용한다.
- 공급자 응답 DTO는 Domain과 Presentation에 노출하지 않는다.

## 현재 제외 범위

- 수동 환율 입력
- 예산·지출 데이터 모델과 화면
- 종료 여행 금액 스냅샷 적용
- 실제 은행 현찰 살 때·팔 때 및 송금 환율

## 검증

- `base=KRW`, 날짜 쿼리와 Frankfurter 배열 응답 역직렬화
- KRW 자기 자신 항목 제외
- VND 환율 역산과 1,000단위 화면 표시
- 빈 응답의 이전 날짜 폴백
- 네트워크 실패 시 마지막 정상 캐시 유지
- Room 5→6 마이그레이션에서 여행 보존과 구 환율 캐시 제거
- 표시 통화 DataStore 유지와 구 통화 코드 정규화
