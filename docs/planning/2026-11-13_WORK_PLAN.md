# 2026-11-13 작업 계획

상태: 2026-11-13 당시의 검토 계획

최근 구현 상태는 [단계별 개발 계획](DEVELOPMENT_PLAN.md)의 현재 진행 상황을 참고한다. 이 문서의 후속 후보는 범위 확정 전 검토 항목이다.

## 1. 목표

완료한 3단계 홈 환율 및 예산·지출 범위를 기준선으로 고정하고, 다음 개발 범위를 사용자와 확정한다. 다음 기능이 확정되기 전에는 데이터 모델이나 화면을 선행 구현하지 않는다.

## 2. 우선순위

### 1순위: 다음 기능 범위 확정

다음 후보 중 하나를 선택한다.

1. 로컬 백업·복원
2. 여행 사진·추가 메모
3. 공유 파일 차기 버전
4. 4단계 여행 일지·사진 갤러리
5. 카드 승인 문자 기반 지출 가져오기

권장 시작점은 `로컬 백업·복원`이다. 로컬 데이터를 기준 상태로 사용하는 현재 제품에서 데이터 손실 방지와 기기 이동을 먼저 보완할 수 있고, 서버·계정 없이 구현할 수 있기 때문이다.

### 2순위: 로컬 백업·복원 요구사항 확정

로컬 백업·복원을 선택한 경우 다음 사항을 먼저 결정한다.

- 여행 파일 공유와 전체 로컬 백업의 목적 및 파일 형식을 분리한다.
- 백업 대상에 여행, 일정, 구조화 장소, 공통·개인 준비물, 체크·완료 상태, 예산, 예상 비용과 지출을 포함할지 확정한다.
- 홈 환율 캐시와 화면 표시 설정처럼 다시 만들 수 있는 데이터의 포함 여부를 결정한다.
- 복원 방식은 `전체 교체`, `새 데이터로 추가`, `선택 복원` 중 최초 지원 범위를 정한다.
- 기존 데이터가 있는 상태에서 덮어쓰기와 중복 데이터가 발생하는 경우의 확인 절차를 정한다.
- 백업 포맷에 버전, 생성 시각과 앱 버전을 두고 이전 포맷을 읽을 수 있는 호환성 원칙을 정한다.
- Android Storage Access Framework를 사용해 별도 저장소 권한 없이 파일을 저장하고 연다.
- 복원 파일 전체를 검증한 뒤 하나의 Room 트랜잭션으로 반영하고 실패 시 기존 데이터를 유지한다.
- 개인 준비물과 완료 상태는 친구에게 전달하는 공유 파일에는 계속 포함하지 않되, 사용자의 개인 전체 백업에는 포함할 수 있도록 정책을 분리한다.

### 3순위: 설계 및 테스트 계획 작성

요구사항이 확정되면 구현 전에 다음 계약을 문서화한다.

- Domain 백업 모델과 버전 정책
- Room Entity와 백업 DTO 사이 Mapper
- Domain의 백업·검증·복원 Repository interface와 UseCase
- Data 계층의 파일 입출력 및 Room 트랜잭션 구현
- Presentation의 파일 선택, 백업 진행, 검증 결과, 충돌 확인과 복원 완료 상태
- 손상 파일, 미지원 버전, 빈 백업, 대용량 데이터, 중복 복원과 트랜잭션 롤백 테스트
- 백업 후 새 DB에서 복원하는 실제 기기 왕복 시나리오

### 4순위: 확정된 최소 범위 구현

사용자가 범위를 확정한 경우에만 테스트를 먼저 추가하고 최소 단위부터 구현한다.

1. 버전이 있는 백업 DTO와 검증 규칙
2. Domain↔DTO Mapper와 Unit Test
3. Room 전체 조회 및 원자적 복원 계약
4. 파일 저장·열기 Repository 구현
5. ViewModel UI state와 Compose 화면 및 Preview
6. 실제 기기 백업→앱 데이터 초기화→복원 왕복 검증

하루 안에 안전하게 완료하기 어려운 경우에는 DTO·검증·Mapper까지를 첫 구현 단위로 제한하고, 불완전한 복원 화면은 노출하지 않는다.

## 3. 4단계를 선택하는 경우

4단계를 시작한다면 첫 범위는 `여행 일지`로 제한하는 것을 우선 검토한다.

- 완료된 여행과 일지의 관계
- 일차별 또는 여행 전체 일지 구조
- 텍스트 메모의 생성·수정·삭제
- 사진은 Photo Picker 기반 선택을 우선하고 직접 촬영은 후속 범위로 분리
- 일지와 사진의 공유 파일·백업 포함 여부
- 사진 파일 수명, 삭제와 고아 파일 정리 정책

지도·장소 API, 클라우드 백업, 서버 계정, 동기화와 iOS 확장은 내일 구현 범위에 포함하지 않는다.

## 4. 완료 조건

- 다음 개발 기능 하나와 제외 범위를 사용자가 확정한다.
- 확정된 기능의 제품 규칙, 데이터 범위와 오류·충돌 처리 정책이 Markdown 문서에 기록된다.
- Room 변경이나 공유 파일 변경이 있다면 마이그레이션·호환성 계획이 작성된다.
- 구현을 시작한 경우 관련 Unit Test, 필요한 Android 계측 테스트, Debug 빌드와 Debug Lint를 통과한다.
- Release 빌드와 Release Lint Vital은 배포 준비 전까지 실행하지 않는다.

## 5. 하지 않을 일

- 범위가 확정되지 않은 3단계·4단계 기능 선행 구현
- 서버, 로그인, 클라우드 자동 동기화 도입
- Google Maps·Places 실제 연동
- `READ_SMS`, 알림 접근 서비스 또는 알림 게시 권한 추가
- 기존 공유 파일 v1·v2의 호환성을 깨는 변경
