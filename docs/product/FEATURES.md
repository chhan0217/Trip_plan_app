# Trip Plan 제품 기능 및 단계별 개발 명세

문서 버전: 2.2
기준일: 2026-11-12
상태: 1·2단계 완료, 3단계 홈 환율과 예산·지출 범위 구현 및 검증 완료

## 1. 제품 정의

Trip Plan은 여행 전에 여행 기간과 날짜별 일정을 만들고, 하나의 파일로 친구에게 전달할 수 있는 로컬 우선 Android 앱이다.

핵심 가치는 다음과 같다.

- 인터넷, 서버, 로그인 없이 여행 계획을 만들고 확인할 수 있다.
- 여행 데이터의 기준 상태는 사용자 기기의 로컬 저장소에 둔다.
- 친구와의 공유는 실시간 동기화가 아니라 여행 계획 파일 전달 방식으로 제공한다.
- 공유받은 사용자는 작성자와 동일한 날짜와 일정 구조를 새 여행으로 불러올 수 있다.
- 가져온 여행은 각 기기에서 독립적으로 수정하며 자동 동기화하지 않는다.

## 2. 단계별 제품 범위

| 단계 | 목표 | 개발 시점 |
|---|---|---|
| 1단계 | 오프라인 여행 계획과 파일 공유 완성 | 개발 및 검증 완료 |
| 2단계 | 여행 준비와 장소 관리 기능 확장 | 개발 및 검증 완료 |
| 3단계 | 예산과 여행 도구 확장 | 홈 환율 및 예산·지출 범위 완료 |
| 4단계 | 여행 기록과 선택적 외부 서비스 검토 | 3단계 이후 |

2단계까지 완료했고 3단계의 홈 환율과 예산·지출 범위를 구현·검증했다. 나머지 3단계 기능과 4단계는 요구사항을 확정한 뒤 진행한다.

## 3. 1단계 핵심 기능

### 3.1 여행 관리

- 여행 생성
- 여행 목록 조회
- 여행 상세 조회
- 여행 제목, 목적지, 날짜와 메모 수정
- 여행 삭제
- 최근 생성·수정 순 여행 목록과 날짜·완료 상태 표시

여행 생성에 필요한 값은 제목, 시작일과 종료일이다. 목적지와 메모는 선택 값으로 취급한다.

### 3.2 날짜별 일정 관리

- 여행 기간을 1일 차부터 마지막 일차까지 자동 계산
- 특정 날짜에 일정 추가
- 일정 제목, 장소, 시작 시간, 종료 시간과 메모 수정
- 일정 삭제
- 같은 날짜 안에서 일정 순서 변경
- 앱을 재실행한 후에도 일정과 순서 유지

장소는 1단계에서 별도 장소 테이블로 관리하지 않고 일정에 문자열로 저장한다. 외부 장소 검색과 좌표가 없어도 모든 일정 기능을 사용할 수 있어야 한다.

### 3.3 여행 파일 내보내기

1. 사용자가 여행 상세 화면에서 파일 공유를 선택한다.
2. 앱이 여행과 모든 날짜별 일정을 공유 DTO로 변환한다.
3. 앱이 버전이 포함된 JSON 기반 여행 파일을 생성한다.
4. 사용자가 Android 공유 화면을 통해 메신저나 파일 앱으로 전달한다.

### 3.4 여행 파일 가져오기

1. 사용자가 전달받은 여행 파일을 앱으로 연다.
2. 앱이 파일 형식, 버전, 필수 필드와 날짜 범위를 검증한다.
3. 앱이 여행 제목, 기간, 일차 수와 일정 수를 미리 보여준다.
4. 사용자가 확인하면 앱이 새 로컬 ID를 생성해 새 여행으로 저장한다.
5. 손상되거나 지원하지 않는 파일은 저장하지 않고 오류를 표시한다.

가져오기의 기본 동작은 기존 여행 덮어쓰기가 아니라 새 여행 생성이다. 같은 파일을 다시 가져오더라도 기존 여행을 자동으로 변경하거나 삭제하지 않는다.

## 4. 1단계 주요 화면

1. 여행 목록 화면
2. 여행 생성 화면
3. 여행 상세 및 날짜별 일정 화면
4. 일정 생성 및 수정 화면
5. 여행 수정 및 삭제 화면
6. 여행 파일 가져오기 미리보기 화면

각 Compose 화면은 기본 상태, 빈 상태, 주요 데이터 상태와 오류 상태를 확인할 수 있는 Preview를 제공한다.

## 5. 1단계 데이터 설계

### 5.1 여행

- 로컬 ID
- 제목
- 목적지
- 시작일
- 종료일
- 설명 또는 메모
- 생성 시각
- 수정 시각

### 5.2 일정

- 로컬 ID
- 소속 여행 ID
- 일정 날짜
- 제목
- 장소 문자열
- 시작 시간과 종료 시간
- 메모
- 같은 날짜 안에서의 순서

### 5.3 확정된 데이터 결정

- Room 기본키는 로컬 자동 증가 ID를 사용한다.
- Room 기본키는 공유 파일에 포함하지 않는다.
- 일차는 별도 `TripDay` 테이블로 저장하지 않고 여행 시작일과 일정 날짜로 계산한다.
- 일정은 소속 여행 ID와 일정 날짜를 직접 가진다.
- 장소는 1단계에서 일정 내부 문자열로 저장한다.
- UUID는 실시간 동기화나 병합 요구가 확정될 때 검토한다.
- 여행 삭제 시 관련 일정은 하나의 트랜잭션 경계 안에서 정리한다.

## 6. 입력 및 데이터 규칙

- 여행 제목은 공백을 제외하고 비어 있을 수 없다.
- 여행 시작일은 종료일보다 늦을 수 없다.
- 일정 제목은 공백을 제외하고 비어 있을 수 없다.
- 일정 날짜는 소속 여행의 시작일과 종료일 사이여야 한다.
- 시작 시간과 종료 시간이 모두 있으면 종료 시간이 시작 시간보다 빠를 수 없다.
- 자정을 넘기는 일정은 1단계에서 지원하지 않는다.
- 일정 순서는 같은 여행의 같은 날짜 안에서 0부터 연속된 값으로 정규화한다.
- 일정 등록과 수정 시 시작 시간이 빠른 순서로 자동 정렬한다.
- 시작 시간이 없는 일정은 시간이 지정된 일정 뒤에 표시하고, 시간이 같으면 기존 사용자 순서를 유지한다.
- 여행 기간을 줄일 때 범위 밖의 일정을 자동 삭제하지 않고 사용자에게 확인한다.
- 가져오기 실패 시 기존 로컬 데이터는 변경하지 않는다.

## 7. 공유 파일 설계 원칙

- 공유 파일 모델은 Domain Model과 Room Entity에서 분리한다.
- 최상위에 파일 형식 버전을 포함한다.
- 여행 제목, 목적지, 날짜 범위, 날짜별 일정, 장소, 시간, 메모와 순서를 포함한다.
- Room 기본키, 기기 경로, 캐시 경로와 UI 상태를 포함하지 않는다.
- 사람이 이해할 수 있는 JSON 구조를 기본으로 한다.
- 포맷이 변경되면 이전 버전을 읽을 수 있는 방향을 우선한다.
- 공유 파일은 특정 시점의 여행 계획 사본이며 실시간 공동 편집을 의미하지 않는다.

## 8. 1단계 기술 기준

- UI: Jetpack Compose, Material 3
- 화면 전환: Navigation 3
- Architecture: Clean Architecture, MVVM, 단방향 상태 흐름
- 상태: StateFlow 기반 단일 UI State
- 비동기 처리: Kotlin Coroutines와 Flow
- 로컬 저장소: RoomDB
- 의존성 주입: Dagger Hilt
- 직렬화: Kotlinx Serialization JSON
- 계층 분리: presentation, domain, data, di

ViewModel은 UseCase에만 의존하고 DAO, Room Entity, 파일 시스템 구현을 직접 참조하지 않는다. 날짜 계산, 입력 검증, 정렬과 파일 변환은 테스트 가능한 순수 로직으로 둔다.

## 9. 1단계 검증 기준

- 오프라인 상태에서 여행을 생성하고 다시 열 수 있다.
- 여행의 모든 날짜에 일정을 추가, 수정, 삭제 및 정렬할 수 있다.
- 앱과 프로세스를 종료한 뒤 다시 실행해도 데이터가 유지된다.
- Room 스키마가 변경되어도 기존 여행 데이터가 보존된다.
- 여행 하나를 파일 하나로 내보낼 수 있다.
- 다른 기기에서 파일을 가져오면 제목, 날짜, 일정, 장소, 메모와 순서가 동일하다.
- 잘못된 파일을 가져와도 기존 데이터가 손상되지 않는다.
- Unit Test, Room 계측 테스트, Compose UI Test, Lint와 Debug·Release 빌드가 통과한다.

## 10. 2단계 구현 완료 범위

2단계는 여행 준비와 장소 관리 편의성을 확장했으며 2026-11-10 배포 전 검증을 완료했다.

- 준비물 체크리스트
- D Day와 여행 완료 상태
- 장소 재사용을 위한 별도 장소 모델
- 수동 주소와 선택적 좌표 저장
- 설정 메뉴와 진입 화면
- 여행 복사
- 최근 생성·수정 순 여행 목록

### 10.1 준비물 공유 범위 확정

- 준비물은 `공통 준비물`과 `개인 준비물`로 구분한다.
- 두 종류 모두 로컬 Room에 저장하고 오프라인에서 조회·수정할 수 있어야 한다.
- 공통 준비물만 여행 공유 파일에 포함해 친구가 같은 항목을 가져올 수 있게 한다.
- 개인 준비물은 공유 파일에서 제외하고 작성자 기기의 화면에만 표시한다.
- 파일을 가져온 공통 준비물은 새 로컬 ID로 저장하며 원본 작성자와 자동 동기화하지 않는다.
- 공통 준비물은 이름, 카테고리, 수량, 메모와 표시 순서를 공유한다.
- 공통 준비물의 체크 완료 여부와 완료 시각은 공유하지 않고 각 기기에서 독립적으로 관리한다.
- 가져온 공통 준비물은 모두 체크되지 않은 상태로 생성한다.
- 공통 준비물이 추가되는 공유 파일 v2를 설계하되 준비물이 없는 v1 파일도 계속 가져올 수 있어야 한다.
- 준비물 생성 시 공통 또는 개인 유형을 정하고 생성 후에는 유형을 변경할 수 없다.
- 담당자 필드는 2단계에 포함하지 않는다.

### 10.2 D-Day와 여행 완료 상태 확정

- `D-N`, `D-Day`, 여행 중 일차와 여행 종료는 시작일·종료일 및 오늘 날짜로 자동 계산한다.
- 날짜가 지났다는 이유만으로 여행을 자동 완료 처리하지 않는다.
- 최종 여행 완료와 완료 취소는 사용자가 직접 선택한다.
- 완료 시각은 로컬 Room에 저장해 앱 재실행 후에도 유지한다.
- 완료한 여행도 조회, 수정과 파일 공유가 가능하며 완료 상태는 데이터 잠금으로 사용하지 않는다.
- 완료 상태는 개인의 정리 상태이므로 공유 파일에는 포함하지 않는다.
- 공유 파일을 가져온 여행은 완료되지 않은 상태로 생성한다.

### 10.3 여행 복사 기본 규칙 확정

- 여행 복사 시 새 여행 이름과 새 날짜 범위를 지정한다.
- 복사 팝업에서 기존 일정 포함 여부를 반드시 묻는다.
- 일정을 포함하고 원본 기간이 새 여행 기간 이내이면 같은 일차 날짜에 복사한다.
- 원본 일차가 더 많으면 모든 원본 일차를 보여주고 초과 일차 수만큼 복사 대상에서 제거하게 한다.
- 남은 일차는 원본 표시 순서를 유지해 새 여행 1일차부터 연속해서 배치한다.
- 일차 제거는 복사 대상 선택일 뿐 원본 여행과 원본 일정은 변경하지 않는다.
- 복사된 여행, 일정에는 모두 새 로컬 ID를 부여한다.
- 여행 완료 상태는 복사하지 않고 미완료 상태로 생성한다.
- 여행과 일정 복사는 하나의 Room 트랜잭션으로 처리한다.

### 10.4 구조화 장소와 외부 공급자 규칙 확정

- 장소는 앱 자체의 공급자 중립적인 구조화 모델로 관리한다.
- 장소 기본 필드는 이름, 주소, 선택적 위도·경도, 데이터 출처와 선택적 외부 식별자다.
- 데이터 출처는 수동 입력 또는 Google 같은 외부 공급자를 구분할 수 있어야 한다.
- Domain, ViewModel과 공유 DTO에 Google SDK 타입을 직접 노출하지 않는다.
- 사용자는 Google 연동 여부와 관계없이 장소를 직접 입력하고 오프라인에서 조회·수정할 수 있다.
- 일정에는 로컬 장소 참조와 장소 이름 사본을 함께 보관해 장소가 삭제되어도 일정 표시값을 유지한다.
- 공유 파일에는 Room 장소 ID를 제외하고 이름, 주소와 선택적 좌표 사본을 포함한다.
- 기존 v1 파일의 장소 문자열은 자유 입력 장소로 계속 가져온다.
- Google 장소 식별자의 저장·공유·캐시 정책은 실제 API 연동 시 최신 정책을 확인한 뒤 확정한다.

### 10.5 언어 지원 범위 확정

- 2단계에서는 다국어 지원과 앱 언어 선택 기능을 구현하지 않는다.
- 당분간 한국어 단일 UI를 유지한다.
- 실제 번역 화면이 없는 상태에서 언어 값만 저장하는 설정은 만들지 않는다.
- 2단계에서는 설정 메뉴와 진입 화면만 만들고 DataStore는 추가하지 않는다.
- 다국어는 추후 별도 요구사항, 번역 리소스와 테스트 범위를 확정한 뒤 검토한다.

### 10.6 장소 입력과 온라인 지도 범위 확정

- 장소는 직접 입력, 지도 핀 지정, Google 장소 검색의 세 가지 방식으로 등록할 수 있게 설계한다.
- 직접 입력은 이름만으로 저장할 수 있으며 주소, 위도·경도와 외부 식별자는 선택 값이다.
- 직접 입력과 저장된 장소 재사용은 Google API와 네트워크 없이 동작해야 한다.
- 지도 핀을 지정하면 사용자가 선택한 좌표를 Room에 저장한다.
- Google 장소를 선택하면 이름, 주소, 좌표와 선택적 외부 식별자 사본을 Room에 저장한다.
- 장소 화면을 열 때마다 Google 정보를 재조회하지 않고 Room의 저장값을 우선 표시한다.
- Google 검색과 지도 표시는 선택적 온라인 기능이며 실패해도 일정 작성과 장소 직접 입력이 가능해야 한다.
- 장소 검색만을 위해 현재 위치 권한을 필수로 요구하지 않는다.
- 주변 장소 검색과 현재 위치 기능은 별도 요구가 생긴 경우에만 권한과 UX를 다시 설계한다.
- 위 Google 검색·지도 핀 기능은 후속 연동 방향이며 초기 2단계에서는 직접 입력과 Room 저장까지만 구현한다.

### 10.7 목록, 설정과 외부 연동 범위 확정

- 여행 검색과 필터는 여행 데이터가 많아질 때 다시 검토하며 2단계에서는 구현하지 않는다.
- 여행 목록은 최근 생성·수정한 여행이 위에 오도록 정렬한다.
- 홈은 여행을 하나의 최근 순 목록으로 표시하고 날짜·완료 상태는 각 카드의 상태 표시로 구분한다.
- 설정은 메뉴와 진입 화면만 만들고 동작하지 않는 설정값이나 DataStore는 미리 추가하지 않는다.
- Google Places, 지도 SDK, API 키와 과금 설정 등 실제 외부 연동은 추후 구현 시 다시 범위를 확정한다.
- 외부 연동을 확정하기 전에는 구조화 장소, 직접 입력과 로컬 저장 기반만 개발한다.

외부 지도와 온라인 장소 검색은 오프라인 핵심 기능을 해치지 않는 선택 기능으로만 검토한다. 외부 API를 사용하지 않아도 장소를 직접 입력하고 일정을 편집할 수 있어야 한다.

## 11. 3단계 추후 개발 범위

3단계는 여행 예산과 보조 도구를 확장한다.

- 여행별 총예산
- 지출 등록과 카테고리 합계
- 통화 코드와 최소 화폐 단위 기반 금액 저장
- 선택적 환율 조회
- 여행 사진과 추가 메모
- 백업 및 복원 기능 확장
- 공유 파일에 준비물과 예산을 포함하는 차기 포맷 검토
- 카드 승인 문자를 복사·붙여넣기하거나 Android 공유 기능으로 전달해 지출 후보를 만드는 로컬 가져오기

환율 API와 사진 저장 정책은 구현 전에 비용, 권한, 캐시와 파일 수명을 별도로 결정한다.

카드 승인 문자 가져오기는 기타 개발의 우선 백로그로 관리한다. 최초 구현은 `READ_SMS` 없이 사용자 주도의 복사·공유 방식으로 제한하고, 금액·통화·시각·사용처·카테고리를 확인 화면에서 확정한 뒤 기존 지출로 저장한다. 알림 자동 감지와 문자함 직접 조회는 개인정보 및 배포 정책 검토 후 별도로 결정한다.

향후 지도·현재 위치·사진 기능을 위해 전경 위치와 카메라 권한 선언을 준비한다. 권한은 앱 시작 시 요청하지 않고 사용자가 현재 위치 또는 직접 촬영 기능을 실행할 때만 요청한다. 지도·장소 입력은 위치 권한 없이도 동작하고 사진 선택은 Android Photo Picker를 우선하며, 백그라운드 위치·저장소·SMS 권한은 현재 추가하지 않는다. 네트워크 연결 여부와 관계없이 로컬 여행 기능은 유지한다.

2026-11-12에는 네트워크·전경 위치·카메라의 공통 기능 상태와 권한 판정 규칙을 추가했다. 허용, 최초 요청, 이유 안내, 영구 거부와 미지원 상태를 테스트 가능한 모델로 분리했으며 실제 위치·카메라 기능이 없는 현재 화면에서는 권한을 요청하지 않는다. 네트워크가 검증되지 않은 상태에서는 환율 원격 호출을 건너뛰고 마지막 정상 Room 캐시를 유지한다.

2026-11-10에 Retrofit, OkHttp와 Kotlinx Serialization 기반으로 Frankfurter v2의 `base=KRW` 환율을 연결했다. 홈 환율 카드, Room 정상 응답 캐시, 이전 날짜 폴백과 DataStore 표시 통화 선택을 구현했으며 별도 API 인증키는 사용하지 않는다. 2026-11-11에는 국가 기반 대표 통화와 예산 기반을 추가하고, Room v9에서 시간 기반 지출을 추가했으며 Room v10에서 실제 사용금액을 지출 기록으로 통합했다.

### 11.0 홈 환율 표시

- 홈에서 선택한 통화의 원화 매매 기준율과 환율 기준일을 표시한다.
- 최초 기본 통화는 `USD`, `JPY`, `EUR`이며 사용자가 VND를 포함한 하나 이상의 통화를 선택할 수 있다.
- 계산용 환율은 외화 1단위당 원화로 저장하고 화면에서만 `100 JPY`, `1,000 VND` 같은 표시 단위를 적용한다.
- 선택값은 DataStore에 저장하고 환율 원본은 Room에 저장한다.
- 앱 시작 시 캐시를 즉시 표시한 뒤 백그라운드에서 갱신한다.
- 당일 응답이 비어 있으면 최대 7일 전까지 이전 기준일을 조회한다.

### 11.1 환율 갱신과 여행별 금액 고정 규칙

- 앱 시작 시 Room의 마지막 정상 환율을 먼저 읽고 최신 환율은 백그라운드에서 요청한다.
- 네트워크 요청 실패나 빈 영업일 응답 때문에 앱 시작과 예산 조회를 막지 않는다.
- 여행 생성·수정 시 ISO 국가 코드를 구조화해 저장하고 국가의 대표 통화를 오프라인에서 자동 결정한다.
- 기본 국가는 대한민국이고 국내 여행의 대표 통화는 KRW다.
- 여행 예산 화면은 통화 직접 입력을 제공하지 않고 여행의 대표 통화를 사용한다.
- 여러 국가 여행도 현재 버전에서는 사용자가 고른 대표 국가 한 곳의 통화를 기준으로 관리한다.
- 예산 생성 후 국가를 변경하면 확인창을 거쳐 기존 예산과 모든 일정 비용을 함께 초기화한다.
- 총예산은 최초 예산 한 건과 여러 건의 추가 예산 내역으로 구성한다.
- 최초·추가 예산은 원화로 입력하며 저장된 최신 정상 환율을 이용해 여행 대표 통화 금액을 자동 계산한다.
- 각 예산 내역에는 원화 입력액, 계산된 대표 통화 금액, 대표 통화 코드, 입력 당시 적용 환율과 환율 기준일을 기록한다.
- 각 예산 내역의 환율과 환산 금액은 여행 날짜 상태와 관계없이 저장 후 자동 재계산하지 않는다.
- 홈의 최신 정상 환율은 새 예산의 자동 환산에 사용하고 기존 예산에는 반영하지 않는다.
- 추가 예산도 원화로 입력하며 추가한 시점의 환율과 대표 통화 환산액을 독립적으로 저장한다.
- 최초·추가 예산은 누적 기록으로 유지하고 개별 수정·삭제 기능은 제공하지 않는다.
- 예산 화면 상단에는 대표 통화 기준 전체 금액과 각 내역의 고정 원화 환산 금액 합계를 표시한다.
- 서로 다른 환율의 예산 내역이 있으면 상단 합계에 특정 환율 하나를 대표 환율로 적용하지 않는다.
- 일정에는 예상 비용 한 건만 직접 입력하고 실제 사용금액은 모두 지출 기록으로 저장한다.
- 일정 카드에서 지출을 추가하면 해당 일정 ID와 시간이 연결되며 상단 지출 추가와 동일한 지출 모델을 사용한다.
- 기존 일정 실제 비용은 Room 9→10 마이그레이션에서 `기타` 카테고리 지출로 변환한다.
- 일정 예상 비용은 여행 대표 통화 또는 KRW를 사용하며 원금액, 적용 환율, 환율 기준일과 원화 환산액을 고정 기록한다.
- 일정표의 비용 영역은 기본적으로 접혀 있고 일정별로 펼쳐 입력한다. 펼침 상태는 로컬 UI 상태로만 관리한다.
- 여행 상세에는 전체 예상 지출, 실제 사용 합계와 실제 사용 기준 남은 예산을 표시한다.
- 선택한 일차 상단에는 해당 날짜의 실제 사용 금액 합계를 표시한다.
- `지출 추가`는 현재 기기 시각을 캡처하고 오늘이 여행 기간 밖이면 선택한 일차와 현재 시각을 사용한다.
- 지출 시각이 일정의 시작 이상·종료 미만이면 해당 일정에 연결하며, 일치하는 일정이 없으면 일차 타임라인에 독립 지출 아이템으로 추가한다.
- 겹치는 일정이 여러 개면 가장 늦게 시작한 일정에 연결하고, 시작·종료 시각이 완전하지 않은 일정은 자동 연결 대상에서 제외한다.
- 지출은 식비·교통·숙박·관광·쇼핑·기타 카테고리와 시간, 대표 통화 금액, 적용 환율, 원화 환산액을 저장한다.
- 지출 입력 기본 통화는 여행 대표 통화이며 사용자가 KRW로 전환하면 같은 입력 시점 환율로 대표 통화 환산액을 즉시 계산한다.
- 개별 지출에는 실제 입력 통화를 주 금액으로, 반대 통화 환산액을 보조 금액으로 표시한다.
- 여행 합계는 대표 통화와 KRW 중 선택한 하나의 통화만 주 금액으로 표시하며 여행별 선택을 DataStore에 저장한다.
- 저장된 선택이 없으면 예정 여행은 KRW, 진행 중 여행은 대표 통화를 기본으로 사용한다.
- 연결된 일정이 삭제되면 지출은 독립 지출로 유지하고 여행이 삭제되면 함께 삭제한다.
- 일정에 연결된 지출과 독립 지출은 금액, 입력 통화, 카테고리와 시간을 수정하거나 확인 후 삭제할 수 있다.
- 지출 수정 시 기존 환율·기준일·생성 시각은 유지하고 원화 환산액만 수정 금액으로 다시 계산한다. 수정한 시간에 맞춰 일정 연결도 다시 계산한다.
- 예산, 일정 비용과 지출은 현재 공유 파일에 포함하지 않는다.

## 12. 4단계 추후 개발 범위

4단계는 완료된 여행을 기록하고 선택적 외부 서비스를 검토한다.

- 여행 일지
- 사진 갤러리
- 여행 통계
- 완료된 여행 기록 조회
- 지도와 장소 API 연동 재검토
- 선택적 클라우드 백업 검토
- 서버 기반 계정이나 동기화 필요성 재평가
- iOS 또는 Kotlin Multiplatform 확장 검토

서버, 계정, 클라우드 동기화와 실시간 공동 편집은 4단계의 확정 기능이 아니다. 사용자 요구와 운영 비용이 확인된 경우에만 별도 프로젝트로 결정한다.

## 14. 단계 전환 원칙

- 현재는 1단계와 2단계 기능까지 구현 및 검증을 완료했다.
- 3단계와 4단계는 문서화된 백로그로 유지한다.
- 이전 단계가 테스트와 실제 사용 흐름까지 검증된 후 다음 단계를 시작한다.
- 후속 기능이 로컬 데이터나 공유 파일에 영향을 주면 구현 전에 마이그레이션 및 호환성 계획을 작성한다.
- 새로운 기능이 핵심 오프라인 동작을 약화시키면 도입하지 않는다.
