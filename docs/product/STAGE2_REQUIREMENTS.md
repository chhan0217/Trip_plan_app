# Trip Plan 2단계 요구사항 확정 기록

문서 버전: 1.1
기준일: 2026-11-10
상태: 핵심 요구사항 구현 및 검증 완료

## 1. 목적

2단계 구현에 적용한 데이터 범위, 공유 정책과 사용자 동작을 기록한다. 확정되지 않은 내용을 임의로 구현하지 않으며, 로컬 우선과 파일 공유 우선 원칙을 유지한다.

## 2. 준비물 체크리스트

### 확정된 요구사항

- 준비물은 `공통 준비물`과 `개인 준비물`로 구분한다.
- 모든 준비물의 기준 데이터는 해당 기기의 Room에 저장한다.
- 공통 준비물은 여행 공유 파일에 포함한다.
- 공유 파일을 가져온 친구는 원본과 같은 공통 준비물 목록을 확인할 수 있어야 한다.
- 개인 준비물은 공유 파일에 포함하지 않는다.
- 개인 준비물은 작성자의 기기 화면에만 표시한다.
- 가져온 공통 준비물은 새 로컬 ID로 저장하며 파일 전달 이후에는 각 기기에서 독립적으로 수정한다.
- 서버 동기화나 실시간 공동 체크는 제공하지 않는다.

### 권장 데이터 구분

```text
PackingItem
├── Shared   : Room 저장 + 공유 파일 포함
└── Personal : Room 저장 + 공유 파일 제외
```

공유 여부를 UI 문자열로만 판단하지 않고 Domain 모델의 명시적인 유형으로 관리한다. 파일 변환 단계에서는 `Shared` 항목만 필터링하며, `Personal` 항목이 공유 DTO에 들어가지 않는 테스트를 반드시 작성한다.

### 체크 상태 공유 규칙

- 공통 준비물의 이름, 카테고리, 수량, 메모와 표시 순서는 공유한다.
- 공통 준비물의 체크 여부와 완료 시각은 공유하지 않는다.
- 파일에서 가져온 공통 준비물은 모두 미완료 상태로 생성한다.
- 체크 상태는 같은 준비물이라도 각 기기에서 독립적으로 관리한다.

상태: 확정

- 준비물 유형은 생성 시 결정하고 공통과 개인 사이의 변경을 허용하지 않는다.
- 기본 필드는 이름, 카테고리, 수량, 메모, 유형, 체크 상태와 표시 순서다.
- 계정과 친구 목록이 없으므로 담당자 필드는 2단계에 포함하지 않는다.
- 같은 이름의 항목을 자동 병합하지 않고 별도 준비물로 유지한다.

## 3. 다른 2단계 기능

### D-Day와 여행 완료 상태

상태: 확정

- 여행 전 D-Day, 여행 중 일차와 여행 종료는 날짜로 자동 계산한다.
- 여행 종료 후에도 자동 완료 처리하지 않고 사용자가 `여행 완료하기`를 선택한다.
- 사용자는 완료 상태를 취소할 수 있다.
- 완료 여부는 Boolean 대신 nullable 완료 시각으로 Room에 저장하는 방향을 사용한다.
- 완료는 목록 정리를 위한 상태이며 완료한 여행의 조회, 수정과 파일 공유를 막지 않는다.
- 완료 상태는 공유 파일에서 제외하고 가져온 여행은 미완료 상태로 생성한다.
- 완료한 여행의 날짜를 미래로 변경하는 경우 완료 취소 여부를 확인한 뒤 변경한다.

### 여행 복사

상태: 확정

- 사용자는 복사 팝업에서 새 여행 이름과 새 날짜 범위를 지정한다.
- 팝업은 기존 일정 포함 여부를 반드시 확인한다.
- 일정 포함을 선택하고 원본 기간이 새 여행 기간 이내이면 같은 일차에 배치한다.
- 원본 여행이 더 길면 팝업에 모든 원본 일차와 일정 개수를 표시한다.
- 사용자는 원본 일차 수와 새 여행 일차 수의 차이만큼 복사 대상 일차를 제거해야 한다.
- 남은 일차는 원본 표시 순서대로 새 여행 1일차부터 연속해서 배치한다.
- 제거 동작은 복사 대상에서만 제외하며 원본 여행과 일정은 변경하지 않는다.
- 여행과 일정에는 새 로컬 ID를 부여하고 완료 상태는 복사하지 않는다.
- 전체 복사는 하나의 Room 트랜잭션으로 처리한다.
- 복사 전 포함·제외되는 일차와 일정 개수를 최종 확인한다.

### 구조화 장소와 Google 연동 방향

상태: 로컬 구조 확정, Google 실제 연동은 추후 재확정

- 장소는 Google에 종속되지 않는 앱 자체 Domain 모델과 Room Entity로 관리한다.
- 장소는 이름, 주소, 선택적 위도·경도, 출처와 선택적 외부 식별자를 가진다.
- 출처는 수동 입력과 Google 같은 외부 공급자를 구분한다.
- 일정은 nullable 로컬 장소 참조와 장소 이름 사본을 함께 가진다.
- 사용자는 구조화 장소를 선택하지 않고 기존처럼 장소 문자열만 직접 입력할 수 있다.
- 장소 삭제 시 일정의 로컬 참조만 해제하고 이름 사본은 유지한다.
- 공유 파일에는 로컬 ID 대신 장소 이름, 주소와 선택적 좌표 사본을 넣는다.
- v1의 장소 문자열을 계속 읽고 새 구조가 없는 장소도 정상 표시한다.
- 외부 API가 없어도 장소 생성, 일정 편집, 파일 가져오기와 기존 장소 조회가 동작해야 한다.
- Google SDK 응답은 data 계층 Mapper에서 앱 모델로 변환하며 ViewModel에 SDK 타입을 노출하지 않는다.
- 장소 등록은 직접 입력, 지도 핀 지정과 Google 장소 검색을 지원하는 방향으로 설계한다.
- 직접 입력은 이름만으로 저장 가능하고 주소와 좌표는 선택 사항이다.
- 지도 핀 지정 시 핀 좌표를 저장하되 Google Places 등록 장소일 필요는 없다.
- Google 장소 선택 시 조회한 이름, 주소, 좌표와 선택적 외부 식별자를 Room에 사본으로 저장한다.
- 저장한 장소를 볼 때 Room 값을 우선 사용하고 매번 Google에 재조회하지 않는다.
- Google 검색과 지도 표시는 네트워크를 사용하는 선택 기능으로 제한한다.
- 네트워크 실패 시 직접 입력, 저장된 장소 선택, 일정 편집과 파일 가져오기는 정상 동작해야 한다.
- 기본 검색에는 현재 위치 권한을 요구하지 않고 주변 검색 기능을 별도로 추가할 때만 검토한다.
- 초기 2단계 구현은 구조화 장소, 직접 입력과 Room 저장까지 진행한다.
- Google Places, 지도 SDK, API 키와 과금 설정은 사용자가 실제 연동을 요청할 때 다시 결정한다.

### 언어 지원

상태: 2단계 제외 확정

- 2단계에서는 다국어와 언어 선택 설정을 구현하지 않는다.
- 한국어 단일 UI를 유지한다.
- 실제 화면 번역 없이 언어 설정 값만 DataStore에 저장하는 기능은 만들지 않는다.
- 다국어는 후속 단계에서 지원 언어, 번역 리소스, 날짜·숫자 형식과 테스트 범위를 별도로 확정한 뒤 검토한다.

### 여행 목록 검색·정렬

상태: 확정

- 2단계에서는 별도 검색과 필터 기능을 추가하지 않는다.
- 여행 데이터가 많아지면 검색과 필터를 후속 요구사항으로 다시 검토한다.
- 현재는 최근 생성 또는 수정된 여행이 목록 상단에 오도록 `updatedAt` 내림차순으로 정렬한다.
- 홈 목록은 상태별 별도 섹션 대신 하나의 최근 순 목록을 사용하고 각 카드에서 D-Day·여행 중·종료·완료 상태를 표시한다.

### 설정 메뉴

상태: 확정

- 2단계에서는 설정 메뉴와 진입 화면만 만든다.
- 실제로 적용할 설정이 없는 상태에서 설정값과 DataStore를 미리 만들지 않는다.
- 다국어는 제외하고 통화·단위 등은 관련 기능이 구현될 때 함께 추가한다.

## 4. 공유 파일 영향

- 현재 공유 파일 v1에는 준비물 필드가 없다.
- 공유 파일 v2에는 공통 준비물만 포함하고 체크 상태와 개인 준비물은 제외한다.
- 공유 파일 v2에는 구조화 장소가 있으면 이름, 주소와 선택적 좌표 사본도 포함한다.
- 새 앱은 준비물이 없는 v1 파일을 정상적으로 가져오고 빈 준비물 목록으로 처리해야 한다.
- 개인 준비물은 어떤 파일 버전에서도 내보내지 않는다.
- 공유 DTO, Room Entity와 Domain Model은 계속 분리한다.
